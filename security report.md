## Security Assessment Summary

A security review was conducted on the Flask backend application, focusing on SQL Injection, access control, information disclosure, file uploads, debug configuration, and Mass Assignment vulnerabilities.

The database layer was reviewed to verify the use of parameterized SQL queries. All queries in `app/*/route.py` and `db/database.py` use `psycopg2` parameterized placeholders (`%s`), with user-provided values passed separately as query parameters. No direct insertion of user input into SQL statements was identified. Two locations use dynamically constructed SQL through f-strings. In `app/auth/route.py`, the dynamic `lookup_column` is restricted to the predefined values `email` and `mobile_number`. In `app/member/route.py`, the dynamic `SET` clause is generated only from a hardcoded `field_map`. Therefore, neither case is considered exploitable SQL Injection, and both are classified as Informational.

A significant access-control vulnerability was identified in `GET /members/find/<memb_id>`. Although the endpoint requires authentication through JWT, it does not verify that the requested member record belongs to the authenticated user. The database query filters only by member ID, allowing an authenticated user to potentially access another member's email, phone number, and membership information by modifying the requested ID. This issue is classified as High severity. The recommended remediation is to enforce ownership checks for regular members or restrict the endpoint to authorized librarian roles. If both members and librarians require access, role-based authorization should be implemented explicitly.

Other member and loan operations were reviewed for similar authorization problems. The routes `DELETE /loan/cancel/<loan_id>`, `POST /loan/borrow`, and `POST /tests/<test_id>/submit` correctly use the authenticated member's identity when accessing relevant records and did not show the same vulnerability. Librarian operations that allow modification of other members or loans are considered consistent with the intended role-based design, provided that librarian authorization is enforced.

Several potential information-disclosure issues were also reviewed. No API route returns `password_hash`, and uploaded `cover_path` values expose only generated filenames rather than server filesystem paths. The quiz functionality returns `answer_text` but does not expose the `is_correct` field, preventing direct disclosure of the answer key. Exception handlers return generic error messages to clients while detailed errors are logged server-side.

The Flask development server was found to expose software version information through response headers such as Werkzeug and Python versions. This is classified as Low severity. In production, the application should be deployed behind an appropriate reverse proxy and production WSGI server, with unnecessary version information removed or generalized.

Debug mode represents a potentially Critical security risk if the application is exposed to the Internet. Werkzeug's interactive debugger can provide capabilities that may lead to arbitrary code execution. Therefore, debug mode must be disabled in production, `DEBUG=False` should be enforced, and the Flask development server should not be used for production deployment.

The file-upload functionality includes appropriate extension and MIME-type allowlists for PNG, JPG, JPEG, and WebP files. Uploaded filenames are replaced with randomly generated UUID-based names, preventing user-controlled filenames from being used directly in filesystem paths and reducing the risk of Path Traversal. Uploaded files are also not directly exposed through a public route.

However, the application currently lacks a request-size limit. Without `MAX_CONTENT_LENGTH`, an attacker may submit excessively large requests or files, potentially causing resource exhaustion or filling available disk space. This is classified as Medium severity. A limit such as `5 MB` should be configured, with oversized requests rejected using HTTP `413 Request Entity Too Large`. In addition, file validation should ideally inspect the actual file signature (Magic Bytes) rather than relying solely on the client-provided MIME type and filename extension.

Finally, Mass Assignment was reviewed across the main creation and update endpoints. Registration does not allow users to assign privileged roles, member endpoints use an explicit field allowlist, loan requests obtain sensitive identifiers from the authenticated user's identity, and test scores are calculated server-side. Book creation and update operations also restrict accepted fields. Therefore, no Mass Assignment vulnerability was identified.

Overall, the assessment found that the application has appropriate parameterized SQL usage and generally good input-control practices. The primary security concern is the broken access control in `GET /members/find/<memb_id>`, followed by the missing upload-size restriction and production configuration issues related to the Flask development server and debug mode. Addressing these issues would significantly improve the application's security posture before production deployment.
